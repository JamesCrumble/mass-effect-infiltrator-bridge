# Как делался Mass Effect Infiltrator Bridge: разбор по шагам

English version: [PORTING_GUIDE.en.md](PORTING_GUIDE.en.md).

Mass Effect Infiltrator 1.0.58 — игра EA / IronMonkey Studios: фреймворк EA Blast, рендер m3g, библиотека
`libMassEffect.so` под `armeabi`. Запуск на телефоне получился быстро, потому что мост и обёртка
уже были сделаны для N.O.V.A. 3. Зато дальше почти каждая проблема оказалась не в порте, а в самой игре или
в её данных: коды касаний, которые у каждой сборки свои; таблица строк с контрольными суммами; ошибка в
сравнении при сортировке, из-за которой игра падала в бою.

Каждый шаг описан одинаково: что было видно, как нашли причину, что и где исправили. Текущее состояние —
в [PROJECT_STATE.md](../PROJECT_STATE.md), сводка — в [README.md](../README.md), исходный порт для
PortMaster описан в [PORT.md](PORT.md).

Состояние: игра проходится — меню, миссии, бой, контрольные точки; при лимите 120 в бою 98–120 кадров/с
(медиана 116) на OnePlus 13s.

## Исходные условия

- Основа — порт EapRules для PortMaster: загрузчик bionic-ELF, фиктивный JNI, переходники libc
  (`src/`, `android/`, `loader/`, `jni/`, `thunks/`).
- Мост GLES, обёртка APK, qemu и инструменты взяты из NOVA3 Bridge.
- Данные игры: APK и архив кэша (~740 МБ после распаковки). SHA1 `libMassEffect.so` сверен с тем, под
  который писался порт.

## Часть 1. Перенос моста

### 1.1. Игра оказалась на GLES2, а не GLES1

- **Что было написано:** в README и комментариях порта — что игра использует GLES1.
- **Как проверили:** по импортам библиотеки — 177 функций `gl*`, из них 64 шейдерных.
- **Вывод:** описание относилось к соседнему порту. Мост из N.O.V.A. 3 (GLES2) подошёл почти без переделки.
- **Правило:** чужому описанию не верить, пока не посмотрел импорты.

### 1.2. Недостающие функции

В мост добавлены вызовы, которых не было у N.O.V.A. 3: `glBindAttribLocation` (новая операция),
`glUniform2/3/4` для float и int, `glUniformMatrix2/3`, `glVertexAttrib*`, `glStencil*Separate`, `glHint`,
`glFinish`, `glDetachShader`, `glValidateProgram`, `glCopyTexImage2D`, `glTexParameter*v`, `glIs*`, `glGet*`.
Генератор — [gen_glbridge.py](../apk/tools/gen_glbridge.py), сторона игры —
[gl_bridge.cpp](../src/gl_bridge.cpp).

### 1.3. Первый запуск

На телефоне с первой установки: qemu стартует, мост работает, главное меню, ~60 кадров/с. Дальше начались
шаги ниже.

## Часть 2. Касания: коды зависят от сборки

- **Видно:** касания доходят до игры, но ничего не происходит.
- **Как нашли:** игра принимает касания через экспорт `NativeOnPointerEvent(env, obj, rawEvent, module, id,
  x, y)`. Значения `rawEvent` не универсальны: их возвращают три экспорта
  `NativeGetIdRawPointerDown/Move/Up`. Порт слал значения другой сборки, и движок их молча отбрасывал.

```sh
readelf --dyn-syms -W libMassEffect.so | grep NativeGetIdRawPointer
arm-linux-gnueabihf-objdump -d --start-address=0x35ae94 --stop-address=0x35aea0 libMassEffect.so
```

  Каждая из трёх функций — три инструкции: `mov r0,#N; add r0,r0,#14; bx lr`.
- **Значения для 1.0.58:** вниз `0x6000e`, движение `0x4000e`, вверх `0x8000e`.
- **Исправление:** [input_bridge.cpp](../android/input_bridge.cpp). Дополнительно `MASSEFFECT_TOUCH=1`
  сообщает движку, что сенсорный экран есть.
- **Правило:** для другой сборки игры значения пересчитываются той же командой. Константу из чужого порта
  не брать.

**Отладка без пальца.** Строки файла `inject.txt` рядом с логом приложение один раз ставит в очередь команд:
`touch 1 x y id`, `touch 0 x y id`, `button a down|up`, `sleep <мс>`. Снимок экрана — `adb shell screencap -p`.

## Часть 3. Картинка и текст

### 3.1. Тёмные силуэты вместо текстур

- **Видно:** в 3D модели чёрные.
- **Как нашли:** обёртки загрузки текстур в [symtab_glprobe.cpp](../src/symtab_glprobe.cpp) искали
  `glGetString`, `glTexImage2D` и `glCompressedTexImage2D` через `SDL_GL_GetProcAddress`. В режиме моста
  контекста SDL нет, функции оказывались NULL. Поддержка DXT/ATC считалась отсутствующей, и загрузки
  терялись без сообщений.
- **Исправление:** `#include "gl_bridge.h"` в этом файле: макрос перенаправляет поиск функций на мост.
- **Правило:** любой файл порта, который ищет функции GL через SDL, обязан подключать `gl_bridge.h`.

### 3.2. Квадраты вместо кириллицы

- **Причина:** движок открывает системный шрифт `/system/fonts/DroidSans.ttf`. Порт для консолей подменял
  его шрифтом игры, в котором кириллицы нет.
- **Исправление:** на Android настоящие системные шрифты есть. `MASSEFFECT_SYSTEM_FONT` указывает на
  `RobotoStatic-Regular.ttf`, подмена отключается.

### 3.3. Пустые кнопки «Да» и «Нет»

- **Видно:** в диалогах подтверждения кнопки без текста.
- **Причина:** русский патч лежит поверх английской таблицы строк и оставляет ключи `NO` и `YES` без значений.
- **Исправление:** [StringsFix.java](../apk/src/com/jamescrumble/meinfiltrator/StringsFix.java) при каждом
  старте дописывает в таблицу «Нет» и «Да».
- **Как устроена таблица** (`strings/ENG_US/masseffect.bin`, формат SBIN v3): чанк `DATA` — пары «ключ,
  индекс значения»; `CHDR` — массив «смещение, длина»; `CDAT` — сами строки.
- **Главная ловушка:** у каждого чанка в заголовке хранится хэш FNV-1 его содержимого. При несовпадении
  движок отвергает таблицу целиком, и все строки превращаются в `XXXXX[KEY]XXXXX`. Первые две попытки
  правки без пересчёта хэшей сломали все строки — в том числе правка всего в три байта.
- **Проверка:** тот же алгоритм написан на Python, результат Java и Python сверен побайтно.

Надпись `XXXXX[STRING_TAPTOAIM_WARNING]XXXXX` — не ошибка порта: такого ключа нет ни в одной таблице игры.

## Часть 4. Падение в бою: дефект движка

- **Видно:** на 18-й минуте, в бою — SIGSEGV в `m3g::Renderer::RenderRenderNode`.
- **Картина:** в списке отрисовки вместо узла `m3g::Node` лежал объект `m3g::Appearance`; вызов виртуального
  метода попадал на данные типа.
- **Версии:** обращение к уже освобождённому узлу либо порча списка при сортировке.
- **Как нашли:** функция сравнения `SortedRenderNode::operator<` **не транзитивна**. Один из её шагов —
  «если у обоих элементов установлен флаг, сравнивать по буферу вершин» — зависит от пары, а не от
  отдельного элемента. `eastl::quick_sort` на таком порядке выходит за конец массива и затаскивает в список
  устаревшие записи прошлых кадров.
- **Как доказали:** собственный код игры (копия байт из библиотеки) был запущен отдельно под qemu-arm на
  случайных данных. 11 из 20 000 сортировок писали за пределы списка, до 90 записей. С исправленным
  сравнением — ни одной. Пары с равным флагом сравниваются как раньше (проверено на 2 млн пар).
- **Исправление:** [render_sort_patch.cpp](../src/render_sort_patch.cpp). `MASSEFFECT_NO_SORT_FIX=1`
  возвращает сравнение движка.
- **Что не доказано:** что именно это вызвало тот конкретный вылет. Это вывод по картине падения; прямая
  проверка — долгая игра без вылета. Версия с NaN отпала: сравнение целочисленное.

## Часть 5. Скорость

### 5.1. Умножение матриц

- **Профиль боя:** четыре функции `Vectormath::Aos::Matrix4` — умножение на вектор, `transform`, умножение
  матриц и `*=` — давали около 27 % выборок.
- **Исправление:** [neon_math_patch.cpp](../src/neon_math_patch.cpp) заменяет их тела кодом на NEON с тем
  же порядком операций. Результат бит-в-бит на обычных числах: тест против оригинальных байт, 400 тысяч
  раундов.
- **Особенность:** выигрыш зависит от процессора под игрой. Поэтому при старте порт сам замеряет оригинал
  и замену и ставит только то, что быстрее с запасом 15 %. Результат — строки `neon math:` в логе.
- **Замер на телефоне:** умножение матриц 6,00 → 2,07 мс на 20 000 вызовов; умножение на вектор — примерно
  паритет.

### 5.2. qemu: NEON без переключения FPCR

- **Причина остатка:** в тогдашнем qemu переход между VFP и NEON стоил записи регистра FPCR.
- **Исправление:** вариант E — NEON f32 считается при обычном FPCR; элементы с денормалями или NaN уходят
  на медленный путь. Патч — `qemu/patches/neon_nofpcr.patch`. Точность проверена тестами `fptest` и
  `neontest` против строгого режима. Позже заменён вариантом F из Shadowgun Bridge.

### 5.3. Ограничитель кадров движка

- **Видно:** игра держит ~61 кадр/с при любом лимите в настройках.
- **Как нашли:** `EA::Blast::System::CreateFpsLimiter` создаёт ограничитель с константой 60
  (`mov r1, #60` по смещению `+0x35c1d0`).
- **Исправление:** `patch_fps_limit` в [patch.cpp](../src/patch.cpp) заменяет константу значением
  `MASSEFFECT_TARGET_FPS`. При лимите 120 меню идёт 117–120 кадров/с.
- **Не проверено:** бой при 30 и 90; зависит ли скорость самой игры от частоты кадров.

### 5.4. Ядра

Замер в бою при лимите 120: на средних ядрах 75–110 кадров/с с просадками до 50–70; на ядрах 6–7 с двумя
кадрами «в полёте» — минимум 98, медиана 116. На быстрых ядрах ~117 даже при потолке частоты 1209 МГц.
Закрепление на ядрах 6–7 включено по умолчанию.

### 5.5. Мелочи, найденные по счётчику системных вызовов

- glibc открывал `/etc/localtime` около 150 раз в секунду. Задана переменная `TZ` из часового пояса
  телефона: 1473 → 7–13 открытий за 10 секунд.
- Одна строка трассировки печаталась каждый кадр: 39 тысяч строк из 47 тысяч в логе. Теперь печатается
  четыре раза.

## Часть 6. Звук

- **Видно:** звук отстаёт, задержка растёт до ~0,75 с.
- **Причина:** вывод SDL через драйвер `disk` тактируется сном, который не равен периоду, и идёт чуть
  быстрее реального времени. Запас копится в pipe и буфере `AudioTrack`.
- **Исправление:** темп задаёт динамик. Сон короче периода (`SDL_DISKAUDIODELAY=15`), pipe ужат до одного
  периода (4096 байт), буфер трека минимальный.

## Что оказалось полезным правилом

1. **Проверять чужие утверждения по бинарнику**: GLES1 против GLES2, коды касаний.
2. **Константы, которые возвращает сама игра, читать из игры** для каждой сборки заново.
3. **Формат данных с контрольными суммами** ломается от любой правки без пересчёта.
4. **Подозрение на дефект движка доказывать отдельно**: вынуть код, прогнать на случайных данных, сравнить
   со своим исправлением.
5. **Замену кода ставить по замеру на месте**, если выигрыш зависит от процессора.

## Что осталось

- «Сверхчувствительный» бег влево и вправо на большом экране. Рабочая гипотеза: пороги движка заданы в
  пикселях под экраны высотой 480–540. Ручки для проверки: `resolution.txt`, `MASSEFFECT_SCREEN_DPI`.
- Ограничение частоты системой — как в остальных проектах.
- Экранные кнопки геймпада.
